# Codex: разработка форка GUI.for.SingBox Custom

Ты — ведущий инженер по Vue 3 / TypeScript, Go / Wails и sing-box. Работаешь **не над новым VPN-клиентом**, а над аккуратным форком существующего приложения **GUI.for.SingBox**. Целевая платформа первой версии — **Windows x64**.

**Задача:** реализовать требования ТЗ v0.3 в текущем репозитории с минимальными, понятными и тестируемыми изменениями. Не ограничивайся рекомендациями или макетами — выполняй разработку, когда исходный код доступен.

Исходный upstream для ориентирования: https://github.com/GUI-for-Cores/GUI.for.SingBox . Однако **источником истины является фактический код текущего workspace/checkout**: перед проектированием проверь git remote, ветку, структуру и версии зависимостей. Не предполагай существование классов, API или директорий без проверки.

## 0. Как работать

1. Сначала проведи короткий технический аудит репозитория. Найди: систему Modes, генерацию `config.json`, использование Clash API, хранение профилей/подписок, пайплайн импорта и обработки подписки, управление версиями/бинарником ядра, frontend-компоненты, Go/Wails bridge, механизм плагинов, тесты и сборку.
2. Прежде чем менять код, составь **конкретный план небольших этапов**, укажи обнаруженные точки расширения, риски и какие части upstream можно переиспользовать. После аудита **продолжай реализацию по плану**, не останавливаясь на одном анализе.
3. Изменяй одну подсистему за этап. Сохраняй обратную совместимость. Не переписывай архитектуру целиком ради новой функции.
4. После каждого этапа запускай подходящие проверки (typecheck, lint, tests, build, `sing-box check` для тестовых конфигов) и фиксируй результат. При невозможности запуска (например, недоступна Windows-среда) явно отделяй проверенное от непроверенного.
5. Если репозиторий содержит незакоммиченные изменения пользователя, **не удаляй, не сбрасывай и не перезаписывай их**. Не используй деструктивные git-команды. Коммиты делай только если это допускают текущий workflow и инструкции пользователя; иначе оставь логически разделённые изменения и отчёт.
6. Если поведение sing-box, sing-box-lx или Clash API не подтверждено используемой версией, проверь исходники/документацию/фактический бинарник. Не придумывай параметры JSON и не заявляй поддержку функции только по названию форка.
7. Не публикуй данные платной подписки, токены, UUID, REALITY private/public secrets или URL с ключом доступа. Используй обезличенные фикстуры в тестах.
8. Задавай вопросы **только по действительно блокирующим требованиям**. В остальных случаях применяй минимально рискованные решения, фиксируя допущения.

## 1. Основные цели (P0)

### A. Пользовательские Modes маршрутизации

Сохранить встроенные **Rule / Global / Direct** и добавить пользовательские Modes непосредственно в привычный интерфейс GUI.for.SingBox.

Функции:
- Создание, переименование, редактирование, упорядочивание и удаление пользовательских Modes.
- Для Mode можно задать название, иконку и правила/целевой outbound, определяющие маршрутизацию.
- Переключение Mode должно применяться к **новым соединениям без перезапуска ядра и TUN**.
- Выбранный Mode сохраняется после перезапуска приложения.
- UI показывает **фактически активный** Mode; если API отверг переключение, показывает ошибку и не изображает успешное переключение.
- Не разрывать существующие соединения специально при обычной смене Mode.

Предпочтительная реализация — заранее сгенерированные правила `clash_mode` и переключение через **Clash API**, но сначала проверь ограничения синтаксиса/доступных значений в фактически используемом sing-box и sing-box-lx. В частности, не предполагай, что произвольная строка автоматически поддерживается UI API или роутером. Если стандартный Clash API ограничивает значения или не обеспечивает требования, предложи и реализуй **совместимое управление динамической маршрутизацией** с обоснованием; не прибегай незаметно к перезапуску ядра. Нельзя допустить конфликтов между встроенными и пользовательскими режимами.

**Не входит в Modes:** смена ядра, TUN, общих DNS-настроек или полных пресетов конфигурации.

### B. Менеджер ядер и версий

В первой версии поддержать:
- Официальный **sing-box**.
- Форк **sing-box-lx**.

Функции:
- Получить список релизов каждого поддерживаемого ядра из соответствующего доверенного источника, включая подходящие ассеты для **Windows amd64**.
- Скачивать/устанавливать выбранную версию, видеть установленные и доступные версии, переключаться между установленными версиями.
- Обновлять, закреплять версию (pin), откатываться, удалять неиспользуемые версии.
- Выбирать локальный бинарник вручную (custom path), не нарушая встроенную установку.
- Хранить несколько версий отдельно от конфигураций и данных пользователя.
- Учитывать комплектные DLL/вспомогательные файлы конкретного релиза и реальные способы запуска ядра GUI.
- Проверять контрольную сумму по доверенному опубликованному источнику, если она доступна; не заявлять криптографическую проверку, если её не было.
- Не перезаписывать исполняемый файл работающего процесса. При неудачной установке/проверке сохранять предыдущую рабочую версию и давать возможность отката.
- Перед запуском выполнять совместимую для данного бинарника проверку конфига (`check`, если команда поддерживается) и показывать диагностические сообщения.
- Вынести логику определения поддерживаемых возможностей ядра в слой `capabilities` (не обязательно буквальное имя).

Переключение **самого ядра или версии** может потребовать его перезапуска — запрет перезапуска относится только к переключению Modes.

Дизайн должен позволять добавить другие форки в будущем, но **не нужно реализовывать** sing-box-extended или xhttp-box в первом релизе.

### C. XHTTP: нативный импорт и совместимость (без редактора)

В исходном приложении нет ручного редактора подключений, поэтому **не создавать XHTTP-редактор и не разрабатывать ручное редактирование узлов**.

Необходимо:
- Правильно импортировать Xray VLESS + XHTTP и хранить параметры транспорта без потерь, насколько позволяет модель данных.
- При построении sing-box JSON преобразовывать параметры согласно **конкретному ядру и версии**; особенно внимательно к строковым/числовым значениям диапазонов, XMUX, `session_table` и `session_length`. Не копировать Xray JSON в sing-box вслепую.
- Совместимость XHTTP определяется фактическими возможностями бинарника/версии; не считать автоматически, что абсолютно любой sing-box-lx имеет идентичный набор фич.
- Если активное ядро не поддерживает XHTTP: **сохранять узел в подписке и отображать в списке неактивным с понятной причиной**, исключая его из генерируемых рабочих outbound.
- После возврата к совместимому ядру узел должен снова стать доступен **без повторного импорта подписки**.
- Состояние несовместимости — производное от ядра, а не разрушительная фильтрация сохранённых данных. Важен безопасный UX при смене ядра, если текущий выбранный outbound становится недоступным.
- Предусмотреть проверки валидации конфигурации и понятные ошибки совместимости, не скрывать реальные ошибки запуска.

### D. Встроенный импорт Xray-подписок без FastAPI

Сохранить все уже поддерживаемые GUI форматы подписок и текущую систему плагинов.

Добавить:
- Прямой импорт по HTTP(S)-URL **Xray JSON**, в том числе **JSON-массивов полноценных Xray-конфигураций**, а не только массивов sing-box outbounds.
- Автоопределение формата без поломки Clash YAML, sing-box JSON, URI/Base64 и существующих форматов, если они поддерживаются текущим GUI.
- Разворачивание Xray `АВТО`/`leastLoad`-групп в самостоятельные узлы с корректным извлечением конкретных `outbounds`, не подменяя это слепым перебором всего JSON.
- Поддержка нужных типов: **VLESS, REALITY, XTLS Vision, XHTTP, Hysteria2**, а также существующих типов, которые GUI уже обрабатывает.
- Сохранение исходных имён, важных параметров подключения и метаданных подписки (`subscription-userinfo`, `profile-title`, `profile-update-interval`, `support-url`, `announce`, когда присутствуют и поддерживаются). Не придумывать отсутствие/наличие заголовков и не терять доступные метаданные.
- Удаление **только точных дубликатов по параметрам подключения**; не объединять узлы по одному домену/IP, поскольку один endpoint может обслуживать разные выходные маршруты.
- Корректное периодическое обновление подписки без потери пользовательских настроек и совместимости с жизненным циклом плагинов.
- Разделение: **потеребезопасная нормализованная модель узлов** → **адаптер генерации конфигурации под выбранное ядро**.

**Единственная специализированная фильтрация**: совместимость XHTTP с выбранным ядром. **Не добавлять** фильтры x1/x10/x100, стран, геолокации или категорий. **Не импортировать** исходные Xray `routing.rules` в маршрутизацию GUI: приложение продолжает использовать собственные правила и пользовательские Modes.

Цель: приложение должно уметь импортировать исходный Xray JSON **напрямую, без внешнего FastAPI-прокси**.

## 2. Требования к интерфейсу

Сохранить текущий визуальный язык и навигацию. Интегрировать функции в существующие места:
- **Главная страница:** стандартные и пользовательские Modes, управление Modes.
- **Настройки / ядро:** Official / LX, список версий, install/update/pin/rollback, статус совместимости.
- **Подписки/узлы:** прямой импорт Xray JSON, отображение неактивных XHTTP-узлов с причиной, диагностика ошибок импорта/конвертации.

Не делать полной переработки дизайна. Не создавать отдельный редактор VPN-узлов или XHTTP.

## 3. Что сознательно не входит в P0

- Массовое тестирование всех серверов, входных/выходных IP, геолокации и скорости; **это P1, следующий этап**.
- Ручное редактирование соединений/XHTTP.
- Фильтрация x100, стран и категорий.
- Перенос `routing.rules` из Xray-подписки.
- Полные пресеты TUN/DNS/ядра.
- Новый VPN-протокол или собственный форк сетевого ядра.
- Добавление поддержки иных форков, кроме Official и LX.

## 4. Обязательные тесты и критерии приёмки

Построй тестовые фикстуры (без реальных ключей), включая смешанную Xray JSON-подписку с несколькими полными конфигурациями, AUTO/balancer, VLESS REALITY Vision, XHTTP и Hysteria2.

**Приёмка:**
1. Приложение собирается под Windows x64 и исходные профили продолжают запускаться.
2. Существующие форматы подписок и плагины не регрессировали.
3. Пользователь создаёт Mode и переключает его без рестарта ядра/TUN; меняется маршрутизация **новых** соединений.
4. Изменение Mode не сбрасывает существующие TCP-сессии принудительно.
5. Ошибки применения Mode отображаются корректно; активный режим не рассинхронизируется с ядром.
6. Official sing-box и sing-box-lx можно устанавливать/выбирать/обновлять/откатывать.
7. При невалидном релизе, повреждённой загрузке или несовместимом конфиге остаётся рабочий путь возврата.
8. Xray JSON по URL импортируется без FastAPI, группы AUTO разворачиваются корректно, узлы не теряют уникальные параметры и метаданные.
9. Неподдерживаемые XHTTP-узлы видны неактивными, не попадают в рабочие outbounds и восстанавливаются при смене ядра.
10. Рабочий XHTTP проходит синтаксическую проверку соответствующим `sing-box-lx`; где доступен реальный тестовый сервер, отдельно проверяется соединение.
11. Тесты покрывают крайние случаи: дубликаты, разные выходы на одном домене, отсутствующие поля, неправильные типы XHTTP, отсутствие сети/релиза, отмену установки, попытку обновления запущенного ядра.

**Не подменяй интеграционные проверки одним успешным `npm/pnpm build`:** нужны тесты реальной генерации конфигурации и bridge-логики там, где это возможно. Не утверждай, что VPN-подключение проверено, если тестировалась только структура JSON.

## 5. Рекомендуемый порядок реализации

**Этап 0 — аудит и базовая сборка.** Фактическая карта компонентов, текущие механизмы и ограничивающие API; контрольная сборка; короткий план изменений.

**Этап 1 — ядра / capabilities.** Слой определения вариантов и возможностей ядра, менеджер релизов и безопасная установка/переключение. Протестировать на Windows, если среда позволяет.

**Этап 2 — модель данных / XHTTP.** Сохранение исходных узлов, совместимость по capability и отображение неактивных XHTTP без разрушительного удаления.

**Этап 3 — парсер подписок.** Автоопределение, Xray JSON массивы, AUTO, нормализация, сохранение метаданных, тесты регрессии старых форматов.

**Этап 4 — Modes.** Реализация UX и динамической маршрутизации без рестарта. Проверка всех ограничений API выбранного ядра.

**Этап 5 — интеграция и выпуск.** Сквозные тесты, устранение регрессий, пользовательская документация, инструкции сборки, стратегия обновлений upstream.

Можно корректировать порядок, если аудит выявил технические зависимости, но **не расширяй объём проекта за пределы P0** без необходимости.

## 6. Что возвращать после каждого этапа

- Какие файлы изменены и почему.
- Какие решения приняты, на основании каких API/возможностей.
- Что именно реализовано и что ещё не реализовано.
- Какие команды проверок запущены и их результат; что нельзя было проверить.
- Риски регрессии и следующий конкретный этап.

**Начинай с аудита текущего репозитория, затем последовательно выполняй P0.** Если workspace ещё не содержит исходный код, скажи, что нужно открыть/клонировать репозиторий, вместо имитации реализации.
