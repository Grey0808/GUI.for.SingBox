# Windows startup isolation audit (2026-11-11)

Scope: checkout based on `09fff91`, Wails 2.17.0. Read-only source inspection; no GUI launch, registry query/write, IPC delivery or interaction with the running VPN.

| Area | Actual code path | Isolation / limitation |
| --- | --- | --- |
| Data directory | `bridge.CreateApp` → `parseArgs` → `initDataDir`, then `resolvePath` for `data/...` | Explicit/portable/default layouts exist. `initDataDir` creates the chosen directory and resolves symlinks. Extraction and config load happen before the Wails instance lock. A fresh explicit directory is essential; no live data was inspected or copied. |
| Instance ID | `main.go` `SingleInstanceLock.UniqueId` | `AppId` + first 8 SHA-256 bytes of resolved `Env.DataDir`; multiple-instance bypass uses a timestamp. An executable rename alone does not isolate this ID. |
| Windows lock and IPC | Installed Wails `internal/frontend/desktop/windows/single_instance.go`, `SetupSingleInstance` | `wails-app-<id>` names the mutex and hidden message window. Existing mutex/window receives launch args through `WM_COPYDATA`; sender exits. `OnSecondInstanceLaunch` focuses the receiver and emits `onLaunchApp`. No lock was acquired or IPC sent for this audit. |
| Deep links | `useAppBootstrap` / `useAppLifecycle.handleLaunchApp` | Cold and warm args can add a subscription via `import-remote-profile`/supported URI forms. No deep link or shell protocol registration was invoked. Exact dedicated data-dir and no URL args are necessary for a safe dry startup, but insufficient to isolate all native effects. |
| Native startup | `main.go` `OnStartup` → `InitializeNotifications`, `trayStart` | Tray/notifications run before frontend settings can opt out. Wails' Windows `notifications.go` `getGUID`/`InitializeNotifications` reads/creates `HKCU\Software\Classes\AppUserModelId\<exe-basename>` and writes `HKCU\Software\Classes\CLSID\<GUID>\LocalServer32`; registers a COM class factory. Keys/GUID are not scoped to data-dir. Windows notification cleanup is a no-op. |
| Frontend bootstrap | `useAppBootstrap` | Loads profiles/subscriptions/plugins/scheduled tasks, handles launch args, runs startup/ready plugin hooks, then initializes kernel state. Reusing a live data directory could execute user plugins/tasks or reconnect/auto-start a core. Tests bypass this bootstrap entirely. |
| Start/exit | `kernelApi.initCoreState`, `helper.exitApp`, stores/settings | A saved PID and auto-start flags affect attachment/start. Exit can stop a running core and clear proxy when configured. Fresh test data has no PID/core/plugins/tasks; auto-start/restart/proxy/DNS/close-core-on-exit are disabled. Native lifecycle has not been exercised on this host. |

Decision: **do not launch the native test GUI on the active-VPN machine**. A separate data directory is not proof that notification registration, native IPC or all startup effects cannot touch a pre-existing application. No new product flag or runtime bypass was added to work around the user's safety restriction.

Available substitute: compile actual Vue SFC scripts and templates with the already installed Vue compiler, mount them into an inert in-memory Vue renderer and drive their input/click events. Primitive widgets are adapters, Wails imports are explicitly mocked, unknown imports fail, file writes stay in memory and the only new HTTP integration server binds `127.0.0.1:0`. These tests cover component wiring/state and subscription conversion without native startup or CSS/WebView2 claims. Windows bridge tests separately exercise real filesystem/process-identity operations solely on test-owned files/PID. See [manual acceptance](../MANUAL_TESTING.md) for the remaining native scenarios.
